# Required local database contracts

Run from the repository checkout containing the candidate migrations:

```sh
npm run prepare:contracts
```

Preparation prints a complete `CONTRACT_STACK_DIR` command with its actual task directory. Run that exact command from this same checkout.

The receipt's `candidateDigest` binds application adapters, suites, helpers, runners, fixture bytes, package lock and configuration as well as migrations. A source change during the run invalidates its result and requires the complete tier to run again.

Preparation creates a new random `paisaxe-contracts-<12 hex digits>` Supabase project in a new task directory. It never accepts an existing directory or resets the shared `paisaxe` project. It uses a local Unix Docker socket, a separately labelled internal Docker network, random nondefault ports, candidate migrations and the repository seed. It copies no `.env` files, provider credentials, linked project references or remote configuration. The internal network prevents historical migration webhook URLs from sending provider traffic. A detached relay binds only literal IPv4 loopback and forwards to fixed DB/gateway targets through the owned database container with Docker exec. This keeps the internal network isolated when Docker provides no live published ports. A private Unix control socket proves project, nonce, source digest and listener ownership; the relay limits active connections and deadlines and expires after one hour. Preparation verifies the running DB and gateway containers before its fresh-project reset, then disables webhook destinations and cron jobs through cron.alter_job in that task database. Before capturing its complete schema baseline, preparation opens a public Realtime channel and waits for the service to initialize its messages publication. It checks exact partitioned-root membership through `pg_publication_rel`, then closes the channel and WebSocket. The partition-expanding `pg_publication_tables` view does not identify that root reliably. No manual publication DDL or schema exclusions are used. `contracts-stack.json` records ownership, database schema and candidate migration identity; it contains no API keys.

The runner requires `CONTRACT_STACK_DIR`. It verifies the task directory, random project ID, literal loopback endpoints, actual Docker labels/network and owned loopback transport, database ownership comment, installed migration versions and schema digest. An unchanged filename with changed migration bytes invalidates preparation. The runner obtains local demo JWTs from that stack's `supabase status`, checks their roles/expiry and requires real anon and service-role reads of the known seeded maintenance flag. Unknown tables, invalid credentials, connection failures and arbitrary HTTP responses cannot satisfy these positive controls.

The PostgreSQL `psql` client is a prerequisite for the required tier. The runner checks `psql --version` and records its version. It supplies the validated task URL and database comment marker to the shared SQL fixture helper. Each native connection checks the marker before executing fixture SQL, uses literal IPv4 loopback and a nonshared port, ignores psqlrc and inherited libpq redirects, and keeps the password out of process arguments. Invalid targets, missing clients, marker mismatch and SQL failures stop the run without a Docker fallback. Ordinary tests retain their original Docker path when this explicit native mode is absent. This avoids repeated Docker inspection overhead without pooling connections or increasing timeout budgets.

Every `src/**/*.postgrest-rls.test.ts` and `src/**/*.postgrest-integration.test.ts` file is discovered, including future additions. The original 15 suites and the five Phase 3 database-boundary, retention, pg_net, application-consumer and Realtime suites are also required by name, so deleting one does not silently narrow the gate. Vitest uses the existing repository configuration and real local Supabase helpers, with one worker and file execution in sequence. Inherited provider credentials, Node preload options and remote Supabase endpoints are excluded. The unique run directory supplies an empty Vite environment directory instead of the checkout's ignored dotenv files.

Zero collected cases, missing/extra report suites, any skipped/pending/todo/failed case, failed hooks or cleanup, malformed/inconsistent reports, missing fresh reports, nonzero process exit, timeouts and post-run schema/network failures all fail the command. Each invocation uses a new private report path. Its `receipt.json` records exact suites, case names, migration identity, positive controls and failure reasons without keys. The offline provider fixture checker runs before database admission so its unverified disclosures remain visible when Docker is unavailable. Provider fixture qualification and live availability are separate evidence.

If preparation fails, its `preparation-failed.json` records the exact disposable project for inspection. Restore local Docker access and rerun preparation from the candidate checkout; a new preparation does not reset the failed task or any shared stack. Inspect that exact project before stopping its containers or removing its labelled network. If migrations or schema changed, prepare a new task instead of editing its marker. If cases or cleanup fail, repair them and rerun the whole required tier; an earlier report cannot satisfy the rerun.

This runner does not reset an existing stack, publish code, run provider captures or enable production retention. Every task container must remain solely on its internal network. Prepared relay listeners bind only 127.0.0.1; a missing or mismatched relay fails admission. A failed preparation stops its owned relay and preserves the task identity and containers for inspection.

The resumed session permits Docker, loopback listeners and Git writes. Focused runner fixtures establish admission/report behavior; final acceptance still requires the fresh candidate stack, actual pg_net delivery, full authorization matrix and cleanup on unchanged source inputs. Several existing suites exercise real PostgREST while replacing outer application seams; those seams are not proof of the full unmocked application behavior. The actual local Realtime probe waits for the `postgres_changes` system acknowledgment, synchronizes the installed poller's existing publication refresh and proves its expected active temporary wal2json slot before the single enabled-change write (`src/lib/feature-flag-realtime.postgrest-integration.test.ts:16`, `src/lib/feature-flag-realtime.postgrest-integration.test.ts:91`). Neither websocket `SUBSCRIBED` nor the system acknowledgment alone proves replication readiness: the warm idle poller can acknowledge while awaiting its periodic publication refresh. This race was reproduced as a missing-slot failure; removing the fixture refresh also fails. Service RPC requires actual native task database identity and an immutable Realtime container ID on the exact nonce-owned sole internal network; it refuses ordinary shared/default stacks. The probe still requires a delivered anonymous event and checks the complete event payload for private configuration. It restores temporary publication membership and canonical values, including SQL NULL, before the schema cleanup check. No sleep, event retry or larger timeout substitutes for readiness.


The native full-validation aggregate runs the named `Run required database contracts` step through `scripts/ci-contracts.mjs`. It prepares a fresh owned stack, runs the complete required tier and stops only its validated immutable container IDs and owned relay. A preparation, contract, provider qualification or cleanup failure fails the step. Failed preparations preserve their task for inspection; the wrapper leaves volumes and networks for hosted runner disposal. This step is required in full/main/release and lean-nightly evidence; CI Fast and the retained original workflow definitions are unchanged.

The wrapper requires `RUNNER_TEMP` and `CI_CONTRACT_RECEIPT_DIR`, with the latter physically confined inside the former. Only the whitelisted `receipt.json` summary is uploaded: status, fixed failure class, counts, provider qualification, candidate/migration digests and task project identity. Detailed test reports remain private. Local source and fixture tests do not establish hosted adoption, execution cost or flake rate; those remain unmeasured until a separately authorized exact-commit push and native run.

The migration source validator (`scripts/check-migrations.ts:410`, regression fixtures at `scripts/check-migrations.test.ts:163`) accepts equivalent `SET search_path=''`, spaced and `TO` syntax. It tracks the final setting, including quoted configuration identifiers, and skips quoted option values so those strings cannot masquerade as a safe declaration. Unsafe lists, escaped nonempty strings, later overrides and dollar-quoted masking are regression tested. The installed four compact retention declarations were independently checked through `pg_proc.proconfig`; migration bytes remained unchanged.
