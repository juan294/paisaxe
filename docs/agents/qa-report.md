## Root Cause Analysis

### Primary failure: HTTP 500 from `/api/chat`

The QA test helper (`sendChatMessage` at `src/tests/qa/llm-quality.test.ts:57`) calls `POST /api/chat` with CSRF headers. All non-safety tests return HTTP 500. Safety tests pass because they use injection/override prompts that may be caught earlier in the pipeline before the failure point.

**Most likely causes, in priority order:**

**1. Wave 1 chat remediation regression (highest probability)**

Recent commits affecting the chat pipeline:
- `9d85d8d8` — Merge branch 'remediate/w1-chat' into develop
- `3f0826f4` — fix: route sensitive server errors through logger
- `77359718` — fix: isolate logger sanitization from edge runtime

The logger isolation fix (`77359718`) changes how errors are processed through the logger. If the chat route imports a logger that has an initialization issue (especially in test/dev context), every request could fail at the logger setup stage. The 500 errors come back very quickly (124-321ms) — fast enough that external API calls (Voyage AI, Claude) may not even be reached, suggesting a synchronous initialization or import failure.

**2. Environment variable missing or malformed**

The chat route imports Anthropic SDK, Voyage AI, and Supabase clients. If any of these env vars are missing in the QA test environment (ANTHROPIC_API_KEY, VOYAGE_API_KEY, NEXT_PUBLIC_SUPABASE_URL), the route throws and returns 500. Recent security agent work (`60e50a3`) documents SUPABASE_SERVICE_ROLE_KEY — if a new required env var was added without updating the test environment, this would cause consistent 500s.

**3. Edge runtime incompatibility**

The journey test output includes:
```
[WebServer] Warning: Using edge runtime on a page currently disables static generation for that page
```
If the chat route was moved to or affected by edge runtime configuration, Node.js-only APIs (used by pino logger, CSRF validation, or crypto) would fail silently as HTTP 500.

**Why safety tests pass but others fail:**

The Safety & Security tests use prompts that trigger early rejection paths (injection detection at `src/lib/chat-safety.ts`). If the safety check short-circuits before the failing code path, those tests pass while all tests that reach the RAG/embedding stage fail. This pattern confirms the failure is in the post-safety portion of the pipeline: embeddings, vector search, or Claude API call.

### Secondary failure: HTTP 429 rate limiting

Two Response Quality tests received 429. The test has exponential backoff retry logic (2000ms × attempt), but the 6-second response times confirm retries occurred before final failure. These 429 errors are likely a downstream effect: the 7 preceding tests may have triggered rate limit accumulation on Anthropic or Voyage AI, with 429 manifesting on the final 2 tests. **This is not an independent issue** — fixing the 500 errors will likely resolve the 429s as well (fewer requests, lower rate limit exposure).

Inspect the response body — in dev mode it includes the error message and stack trace. Look for:

- Edge runtime incompatibility in pino logger

**Check**: `src/app/api/chat/route.ts` imports and whether any new logger imports were added by the remediation commits. The logger isolation commit (`77359718`) is the prime suspect.

### Priority 2 — HIGH: Check logger initialization in API routes

The commit `77359718` ("fix: isolate logger sanitization from edge runtime") suggests the logger was being used in an edge-incompatible way. If the chat route was updated to import the new logger but the logger still has an initialization bug in the Node.js runtime, all requests through that route fail.

**Check**: `src/lib/logger.ts` or equivalent — verify it initializes without throwing when `NODE_ENV=test` or in the QA test dev server context.

### Priority 3 — MEDIUM: Add rate limit retry configuration to QA tests

The test retry logic (`src/tests/qa/llm-quality.test.ts` sendChatMessage) uses 2000ms base delay. If 10 concurrent tests hit the API, the accumulated rate limit can still exceed limits. Consider:
- Adding a delay between test categories
- Reducing `QA_TESTS_PER_CATEGORY` to 2 for rate-sensitive runs
- Adding jitter to the retry delay

### Priority 4 — LOW: Address persistent E2E gaps (see gap analysis below)

The `/api/mcp/*` coverage gap has been flagged for 10 consecutive QA runs. These external-facing endpoints used by ElevenLabs remain at 0% E2E coverage.
