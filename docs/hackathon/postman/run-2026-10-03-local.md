## Found during the first run (outside this unit), since fixed

- `GET /api/booking/bookings/<capability>` answers `Referrer-Policy:
  strict-origin-when-cross-origin`, not the `no-referrer` that the route sets in
  `CAPABILITY_HEADERS` (`src/lib/booking/view.ts`). The site-wide `headers()` entry in
  `next.config.ts` (`source: "/(.*)"`) overrides it for `/api/` paths, and only `/booking/` and
  `/operator/` get `no-referrer` there. `Cache-Control: private, no-store` and
  `X-Robots-Tag: noindex` do arrive. The collection asserts those two and leaves this to the
  owner of `next.config.ts`.
- An earlier attempt failed at payment start with a duplicate `payments.order_id`. The
  restarted PayPal mock reissued an order id already stored by a previous run. The mock now
  takes an opt-in `idSalt`, and the runner passes a random one on each start.

The first was fixed in Phase 5 (notes file, Phase 5 deviation 12): capability API paths get
`no-referrer` from `next.config.ts`. The second was fixed by the mock's `idSalt`. The same run
also showed that a confirm on a booking outside the cancellation flow answered 200; it now
answers 409 `invalid_state` (same deviation).
